# Predictive Maintenance for Manufacturing — Project 21

An end-to-end classifier that flags the operating days on which a machine is likely to fail, using daily sensor telemetry. The project covers data validation, leakage-safe feature engineering, device-grouped splitting, five competing models (including three ensembles), imbalance-aware evaluation, error analysis and a runnable scoring prototype.

## 1. Problem statement

Unplanned machine stoppages cost manufacturers production time and money. Reactive repair means the failure has already happened; periodic maintenance replaces parts that may still be healthy. Predictive maintenance sits between the two: if sensor readings suggest a failure is imminent, the maintenance team can inspect that specific machine before it stops.

- **Users:** maintenance planners and plant engineers responsible for a fleet of machines.
- **Input:** one row per machine per day — nine anonymised sensor metrics plus the date.
- **Output:** a probability of failure for that day and an actionable `OK` / `MAINTENANCE` decision.
- **Benefit:** fewer surprise stoppages, fewer unnecessary inspections, and a ranking of machines by risk so limited technician time is spent where it matters.

This is a decision-support demonstration, not a certified safety system.

## 2. Dataset

| Property | Value |
| --- | --- |
| File | `data/predictive_maintenance_dataset.csv` (copy of the supplied dataset) |
| Records | 124,493 device-days after removing 1 duplicate device-date row |
| Devices | 1,169 |
| Observation window | 1 Jan 2015 – 2 Nov 2015 (304 distinct dates) |
| Features | `metric1`…`metric9` (anonymised, numerical; `metric8` is an exact copy of `metric7` and is dropped) |
| Target | `failure` — 1 = the device failed that day (106 positive days, 0.085%), 0 = normal |
| Devices with a failure | 106 (at most one failure per device; for 101 of them it is the last recorded day) |
| Missing values | none |

**Limitations.** The metrics are anonymised, so their physical meaning and units are unknown; the fleet, plant and failure type are not recorded; there are no maintenance logs or labels for "near misses". With only 106 positives, estimates of precision and recall are noisy. These limits are reflected in the interpretation in §7 and §9.

`train.py` accepts `--data`, `--output-dir`, `--seed` and `--cpu-only`. ## 6. Methodology

### 6.1 Preprocessing

Dates are parsed as `m/d/YYYY`, rows are de-duplicated on `(device, date)` and sorted by device then date. No missing values were present. `metric8` is removed because it duplicates `metric7`. Scaling is applied **inside** the logistic-regression pipeline only; tree models use the raw values. No target-derived aggregates are used anywhere.

### 6.2 Features (20 numeric features)

- 8 raw metrics (`metric1`–`metric7`, `metric9`).
- Calendar fields: `day_index` (days since a fixed 2015-01-01 origin), `month`, `day_of_week`.
- Fleet context: `device_age_days` (days since that device's first reading).
- For each of the 8 metrics, a z-score against that device's **own expanding history**: the mean and standard deviation of prior readings only, shifted by one day. A suddenly unusual reading therefore stands out even when the device's normal range differs from the fleet's. Early readings with fewer than three observations fall back to 0.

All feature construction is causal — a row never sees a future reading or its own label — so the same code is used for training and for new readings in `predict.py`.

### 6.3 Splitting and validation

The split is **by device**, not by row: all readings of a machine stay together (70% train / 15% validation / 15% test, stratified on whether the device ever failed). This prevents a model from memorising individual machines and measures performance on unseen devices. Result: 85,041 / 21,116 / 18,336 rows with 74 / 16 / 16 failures respectively.

Hyperparameters are selected with a small randomised search (4 candidates per ensemble, 3-fold `StratifiedGroupKFold` over training devices) scored by average precision (PR-AUC).

### 6.4 Models compared

| Model | Role | Notes |
| --- | --- | --- |
| Logistic regression | simple baseline | balanced class weights, standardised inputs |
| Decision tree | interpretable single model | depth 8, minimum 20 samples per leaf, balanced weights |
| Random forest | bagging ensemble | 300 trees, `balanced_subsample` weights |
| Gradient boosting | boosting ensemble | 200 trees, depth/learning-rate searched |
| XGBoost | boosting ensemble | GPU histogram training; depth, learning rate, minimum child weight and `scale_pos_weight` searched |

The ensembles are compared against their individual components as required for an ensemble project; fit times are reported alongside scores.

### 6.5 Imbalance and decision threshold

Accuracy would be misleading here — predicting "never fails" already scores 99.9%. Ranking quality is measured with **PR-AUC** (primary) and ROC-AUC (secondary). The operating threshold is *not* left at 0.5: it is chosen on the validation split to maximise F1, then applied once to the untouched test split. Precision, recall, F1 and a confusion matrix are reported at that threshold.

## 7. Results

_Populated from the saved run; see `outputs/metrics.json` and `outputs/model_comparison.csv` for full detail._

**Model comparison** (random search on training devices; scores on validation and untouched test splits):

| Model | Val PR-AUC | Val ROC-AUC | Test PR-AUC | Test ROC-AUC | Fit time (s) |
| --- | ---: | ---: | ---: | ---: | ---: |
| logistic_regression | 0.0392 | 0.8637 | 0.0771 | 0.8125 | 0.4 |
| decision_tree | 0.0399 | 0.7013 | 0.0241 | 0.6519 | 0.5 |
| random_forest | 0.0547 | 0.9261 | 0.1580 | 0.8335 | 26.4 |
| gradient_boosting | 0.0246 | 0.8592 | 0.1130 | 0.8049 | 269.8 |
| xgboost | 0.1345 | 0.9078 | 0.1343 | 0.9274 | 10.4 |

**Selected model:** `xgboost` with parameters `{"learning_rate": 0.03, "max_depth": 3, "min_child_weight": 1, "scale_pos_weight": 5}`. It had the best validation PR-AUC and the best test ROC-AUC.

At the validation-tuned threshold of **0.1790**, the test results are precision **0.200**, recall **0.312**, F1 **0.244** (5 true positives, 20 false positives, 11 false negatives, 18300 true negatives). The threshold-independent test PR-AUC is **0.1343** and ROC-AUC is **0.9274**, against a no-skill PR-AUC of 0.0009 — roughly 154 times the random-ranking baseline. A classifier that never alerts scores 0.9989 accuracy, which is why accuracy is not used for selection.

The five most influential features by permutation importance on the test split were `metric7`, `day_of_week`, `metric2`, `metric2_z`, `metric1`. Raw sensor levels dominate, but the calendar and at least one deviation score also contribute, which supports keeping the history-based features. Importance ranks predictive dependence, not physical causation, and is noisy with only 16 test failures.

## 8. Prototype

`scripts/predict.py` rebuilds the same 20 features, applies the saved threshold and prints a decision. Input CSV columns:

```
date,device,metric1,metric2,metric3,metric4,metric5,metric6,metric7,metric8,metric9
1/1/2015,S1F01085,215630672,55,0,52,6,407438,0,0,7
```

`metric8` is accepted but ignored. Include the device's recent history in the file: the expanding baselines are computed from the rows supplied, so a single isolated reading has zero deviation features. Example output from the built-in demo (last readings of two devices that failed):

```
  device       date  failure_probability    decision  actual_failure
S1F0RRB1 2015-01-05             0.078369          OK               1
S1F0CTDN 2015-01-07             0.551235 MAINTENANCE               1
```

The notebook shows the same scoring function interactively and displays the diagnostic plots.

## 9. Error analysis and limitations

- The confusion matrix in `outputs/figures/confusion_matrix.png` and the row-level scores in `outputs/test_predictions.csv` show exactly which days were missed (false negatives) and which triggered unnecessary inspection (false positives).
- PR-AUC is high relative to the 0.085% no-skill baseline but the operating point is conservative: most failures are still missed at the F1-optimal threshold. Raising recall would increase false positives; the threshold should be set from the plant's relative cost of an unplanned stoppage versus an unnecessary inspection.
- Permutation importance identifies which readings the model relies on; it describes **predictive dependence**, not physical causation, and is unstable with only 16 test failures.
- With 1,169 devices and anonymised metrics, the model is fleet-specific. It must be retrained on new telemetry before deployment, and monitored for drift.

## 10. Ethics and responsible use

The dataset contains device identifiers and measurements, not personal data. In a real deployment, sensor histories can still be linked to workers or sites, so access should be limited and retention justified. The model is decision support: it should schedule inspections, not automatically shut down equipment or overrule a qualified engineer. False negatives carry a safety risk, false positives carry cost and unnecessary intervention; both must be reviewed. Predictions must not be presented as certified failure diagnoses, and the system needs human oversight, audit trails and periodic revalidation.

## 11. Reproducibility
